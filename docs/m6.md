# M6: a native client, then Android

The milestone's acceptance line is "phone drives a real session over the socket".
The parity audit comes last, because it is what says whether the rest was the
right work.

## What exists

- `docs/protocol.md` — the frozen contract: frames, methods, events, errors.
- `src/cli/main.c` — a working client, but **static inside the CLI**: `wd_client`,
  `client_connect`, `client_handshake`, `client_request`, the event reader and
  the frame helpers live in that one file. Nothing else can link them.
- `tests/` — several gates act as clients (the `request` helper in
  `tests/gate_tool.c` is the most complete example).
- `src/proto/` — `frame.h` and `codec.h` are already shared and carry no CLI
  dependencies.

## The first slice: make the client a library

Nothing else can start until the client is reusable. Move, mechanically and
without behaviour change:

| from `src/cli/main.c` | to `src/client/client.h` / `client.c` |
|---|---|
| `wd_client` | the struct, opaque to callers |
| `client_connect`, `client_handshake` | `wd_client_connect`, `wd_client_handshake` |
| `client_request` | `wd_client_call` |
| the event reader and `pending` queue | `wd_client_next_event` |
| frame read/write helpers | `wd_client_send_frame` / `_read_frame` |

Then the CLI keeps only its argument parsing and printing, and its behaviour must
not change: every gate in the suite that uses the CLI is the regression test.
The new library gets one new dependency — nothing from `src/cli/`.

## The second slice: a native binary

`clients/native/` with a `ward-native` binary that speaks the protocol and
offers what the CLI does, over the library. Gate: it drives a real session
end to end against a daemon started by the test — create, prompt, collect the
turn, resume from the log — with the same assertions `tests/gate_tool.c` makes,
but through the library rather than the CLI.

## Status

Slice one is done: `src/client/` holds the client and the CLI links it.
Slice two is half done: `clients/native/main.c` builds as `ward-native` with
`create`, `prompt` and `resume`, and was smoke-tested against the running daemon
(created a session and sent a prompt).

Its gate is written but not committed, because it exposed a question rather than
a pass: against the fixture daemon the turn reaches the provider, gets its reply,
and then never returns from `wd_turn_prompt` — one reply parsed, then nothing for
forty-five seconds. `gate_tool` drives the same fixture successfully, and the one
difference is that it calls `session.resume` before prompting. So the next
probe is one line: subscribe in `ward-native` before the prompt, re-run the
gate, and see whether the answer arrives. If it does, the daemon needs a
subscriber for a session to progress, which the protocol document does not say
and should.

## The third slice: Android

The phone needs the same framing and handshake over QUIC (already in core, gated
by `gate_quic`) or over a forwarded Unix socket. Two candidate shapes:

1. a Kotlin implementation of `docs/protocol.md` (CBOR + length-prefixed frames +
   the method table), sharing nothing but the document;
2. a C library compiled for Android through the NDK, reused verbatim from the
   second slice.

The second is less code and one protocol implementation; the first is no JNI. The
choice belongs to whoever builds the app, and the audit should record which was
taken and why.

## What the Android client still needs from this repository

Nothing in the tree is a substitute for a device, but three things would let a
Kotlin client be written and reviewed without one:

1. **a golden transcript** — the exact bytes of `hello`, `welcome`,
   `session.create`, `session.prompt` and one `session.resume` burst, captured
   from a real daemon and stored as a fixture, so a re-implementation can be
   diffed rather than guessed at;
2. **the CBOR subset in use** — which major types and lengths actually appear on
   the wire (definite maps and arrays, text, uint, bool, no tags, no indefinite
   forms), so a hand-written encoder does not need a full library;
3. **a conformance harness** — a test that replays the golden transcript through
   whatever client is under test. In C that is a small program; for Kotlin it is
   a JVM test reading the same fixture.

The first two are done and the third exists in its first form:
`tests/transcripts/create.txt` holds the captured frames, and
`tests/conformance_test.c` decodes each of them with `wd_decode` and re-encodes
it, asserting the bytes are identical. That proves the encoder emits the
canonical form a re-implementation must match; pointing the same fixture at a
Kotlin test is what closes the Android row.

The third is the one that makes the Android row `delivered` under this
repository's rule, and it is the reason to capture the transcript now rather
than after the app is written.
